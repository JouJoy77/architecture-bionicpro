## Запуск

Нужны Docker с Compose и Python 3 для создания локальных ключей. Для контейнеров рекомендуется выделить 6 ГБ памяти и около 6 ГБ свободного места на диске. Порты 3000, 8081 и 8082 должны быть свободны.

```bash
bash scripts/setup.sh
docker compose up -d --build
docker compose ps
```

При первом запуске Compose создает БД, импортирует realm, заполняет источники вымышленными данными за семь завершенных суток и запускает Airflow. DAG автоматически обрабатывает эти дни. Первое построение витрины занимает несколько минут после запуска планировщика.

Если на Linux сборка останавливается на `Temporary failure in name resolution`, можно собрать образы через сеть хоста:

```bash
docker compose -f docker-compose.yaml -f docker-compose.build-host.yaml build
docker compose up -d --no-build
```

Этот вариант меняет только сеть сборки. Работающие сервисы сохраняют отдельную Docker-сеть и привязку опубликованных портов к localhost.

| Адрес | Назначение | Вход для локального стенда |
| --- | --- | --- |
| http://localhost:3000 | Приложение | `prothetic1` / `prothetic123` |
| http://localhost:8081 | Keycloak | `admin` / `demo_admin` |
| http://localhost:8082 | Airflow | `admin` / `demo_airflow` |

В приложении доступны следующие сценарии:

- `prothetic1`: два протеза, BP-101 и BP-102.
- `prothetic2`: один протез, BP-201. Пароль `prothetic123`.
- `prothetic3`: пользователь без телеметрии. Пароль `prothetic123`. За обработанный день получит пустой отчет.
- `user1` / `password123` и `admin1` / `admin123`: вход разрешен, доступ к отчетам запрещен.

Демонстрационные пароли не предназначены для внешнего развертывания. Все опубликованные порты привязаны к `127.0.0.1`. `.env` содержит случайные ключи и не включается в Git.

## Как устроен вход

React открывает `/auth/login`. API работает как BFF: создает `code_verifier`, отправляет `code_challenge` с методом `S256` и обменивает код на токены на сервере. Браузер получает только непрозрачную HttpOnly cookie с ID сессии. Access- и refresh-токены хранятся в Redis в зашифрованном виде.

По этой причине `keycloak-js` удален из React: обычный JS-адаптер получает токены в браузере, что противоречит первому пункту задания. PKCE включен в реальном процессе входа, а Keycloak требует `S256` для клиента `reports-frontend`. Это confidential client, его секрет известен только BFF.

Сервис отчетов доступен только внутри Docker-сети. Внешний запрос идет через исходный API: `браузер -> API/BFF -> сервис отчетов -> ClickHouse`.

## API

После входа приложение использует cookie сессии:

```text
GET /auth/session
GET /reports/availability
GET /reports?start_date=2026-11-12&end_date=2026-11-18
GET /reports?start_date=2026-11-12&end_date=2026-11-18&format=csv
POST /auth/logout
```

Даты в примерах нужно заменить на доступные в своем стенде. `start_date` и `end_date` включаются в отчет, часовой пояс UTC. Максимальный период составляет 93 дня. Идентификатор пользователя в запросе не принимается. Параметры `user_id`, `subject` и `device_id` возвращают HTTP 400.

| Код ответа | Значение |
| --- | --- |
| 200 | Готовый отчет; пустой список допустим, если день обработан, но событий нет |
| 400 / 422 | Ошибка параметров или дат |
| 401 | Пользователь не вошел, токен недействителен или сессия завершена |
| 403 | Нет роли для отчетов или не пройдена CSRF-проверка выхода |
| 409 | Хотя бы один день еще не опубликован Airflow; в ответе перечислены эти дни |
| 413 | Слишком большой отчет, нужно уменьшить период |
| 503 | Временно недоступен зависимый сервис |

`/reports/availability` возвращает список завершенных дней, а не только максимальную дату. Это позволяет учитывать пропуски между успешно обработанными интервалами.

## Airflow

DAG `bionicpro_daily_reports` запускается ежедневно в 00:00 UTC. Каждый запуск обрабатывает `[data_interval_start, data_interval_end)`. Включены `catchup=True`, два повтора при ошибке и ограничение `max_active_runs=1`.

Начальная дата фиксируется в `.env` при запуске `scripts/setup.sh`. Она не пересчитывается при каждом разборе DAG. Для повторной обработки дня можно очистить соответствующий task instance в Airflow. Чтобы повторно обработать уже существующий запуск за один день:

```bash
docker compose exec airflow-scheduler airflow tasks clear bionicpro_daily_reports \
  --start-date 2026-11-12T00:00:00+00:00 \
  --end-date 2026-11-12T00:00:00+00:00 --yes
```

Команда сбрасывает задачу выбранного запуска, после чего планировщик выполнит ее снова. Обе даты обозначают его logical date, то есть начало обрабатываемых суток. Выберите существующий запуск из своего набора данных. `airflow dags test` использует правила ручного интервала и для этой операции не подходит. Повторный запуск заменяет партицию целиком, поэтому счетчики не удваиваются. После изменения даты запуска в `.env` потребуется пересоздать контейнеры Airflow. После изменения realm JSON уже импортированный realm автоматически не обновляется: измените его через Keycloak Admin Console или используйте отдельный чистый стенд.

## Проверки

Для локальных тестов рекомендуется Python 3.12, который используется и в контейнерах:

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
.venv/bin/ruff check api reports_service common airflow scripts tests
.venv/bin/python scripts/smoke_test.py --wait-refresh
```

Проверка ETL на настоящих PostgreSQL и ClickHouse:

```bash
docker compose exec -T airflow-scheduler python - < tests/etl_integration.py
```

Она использует специальные тестовые записи за 2019-12-31 и 2020-01-01, после проверки удаляет их. Запускайте ее только на локальном демонстрационном стенде.

Фактические результаты проверки описаны в [отчете](docs/verification.md).
